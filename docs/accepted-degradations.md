# Accepted Degradations

Log of scoring components deliberately weighted to 0 (or otherwise degraded)
while their underlying series keeps fetching and their score keeps computing.
Not deletions: the pillar stays in the YAML config and stays visible in the
UI (greyed, badged) so the number is always inspectable, even at weight 0.
Each entry records why, and what would trigger re-evaluation.

---

## 2026-08-17 — TREND disabled entirely (`trend_enabled: false`)

**Component:** The whole TREND pillar (price MA structure × ADX strength,
±3, weight 0.5), everywhere it was folded in: every FX pair
(`src.economic_compute.compute_instrument`) and every cross-asset instrument
that carries a `trend` factor (`src.crossasset_compute.compute_instrument_score`).

**Change:** `config/pipeline.yaml`: `trend_enabled: false` (new key, default
false). `src/economic_render.py` gates on it — when false: `trend_score_all()`
is never called; no instrument (FX or cross-asset) carries a `trend` or
`trend_detail` key; `compute_crossasset_scores` is called with
`trend_by_symbol=None`; `_freshness()` skips the "price" entry
(`data/price_history.parquet` has no other consumer); `payload.meta.trend_enabled`
is surfaced so `static/economic-chart.js` can drop every TREND trace from the
DOM (column, sub-header, cell, modal section, the "+ TREND" wording in the Σ
tooltip). No scoring file was touched — `economic_compute.py`,
`crossasset_compute.py`, and `trend_score.py` are all unmodified; the flag
is a pure gate in the render layer plus a couple of post-hoc key-strips, and
setting `trend_enabled: true` reproduces today's pre-flag payload
bit-for-bit (see `docs/trend-off-before-after.md`/`.csv`, generated by
`scripts/diag/trend_off_diff.py`, and `tests/test_trend_disabled.py`'s
rollback test).

**Effect:** Every instrument's score renormalizes to FUND + SENTIMENT only
(TREND's weight-0.5 slot drops out of the weighted mean rather than being
zero-filled — same mechanism the existing "trend absent" path already used
for a symbol with no price series). Per `docs/trend-off-before-after.md`
(2026-08-17 snapshot, 37 instruments): 31 instruments' rounded score changes
and 20 instruments' bias label changes — see that file for the full list.
`scripts/econ_refresh.sh`'s MT5 price-export step (and its
`data/price_history.parquet` commit) is commented out, not deleted, since
nothing reads that file while the flag is off.

**Reason:** The MT5 price feed (TREND's sole data source) only runs through
Wine on the operator's Mac — no cloud path, single point of failure, and the
one piece of this pipeline that cannot run on the GitHub-Actions side of the
2026-07-29 calendar/price split. Disabling TREND removes that dependency
from the scored page entirely while keeping every line of the trend engine
intact behind the flag.

**Re-evaluation trigger:** Revisit once TREND has a data source that runs in
CI (or the trend engine rebuild referenced in the 2026-08-16 entry above
lands) — at that point flip `trend_enabled: true`, re-enable the
`price_fetch` step in `scripts/econ_refresh.sh`, and re-run
`scripts/diag/trend_off_diff.py` to confirm the reinstated impact matches
expectations before treating it as the new default.

## 2026-08-16 — Cross-asset `balance_sheet` (liquidity pillar) weight → 0

**Component:** `balance_sheet` sub-component of the `rates` factor, in
`data/crossasset_instruments.yaml`, for all 8 cross-asset instruments
(DJIA, SP500, NASDAQ, DAX, NIKKEI, FTSE100, GOLD, SILVER).

**Change:** `weight: 1.0` → `weight: 0.0` (sign unchanged, component config
key kept). The series (WRBWFRBL, falling back to net_liquidity) keeps
fetching and `compute_liquidity_score()` keeps computing a score; it now
contributes 0 to every instrument's composite. The cell remains visible in
both the cross-asset table and the rate-breakdown modal, greyed, with an
"excluded from composite" badge.

**Reason:** The 21-bd rate-of-change on reserves conflates calendar TGA
flows (debt-ceiling drawdowns, quarter-end settlement, tax-date swings) with
genuine regime change in the liquidity backdrop. Those calendar-driven moves
in WRBWFRBL can dominate a 21-bd window without reflecting an actual
tightening/easing regime shift, so the pillar's signal-to-noise ratio at the
current horizon is not high enough to carry weight in the composite.

**Re-evaluation trigger:** Revisit after the trend engine rebuild lands —
that work is expected to change how regime-vs-noise is separated for
momentum-style pillars generally, and the liquidity pillar's viability
should be reassessed under whatever windowing/smoothing approach comes out
of it, rather than by further hand-tuning the current 21-bd/5-day-smooth
band scorer in isolation.
